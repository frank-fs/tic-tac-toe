# Frank 7.2.0 → 7.3.2: AI-Assisted Dev-Experience Assessment

**Date:** 2026-08-10
**Method:** Case study, not a survey. The evidence here comes from actually planning the migration in `docs/superpowers/plans/2026-08-10-frank-7.3.2-upgrade.md` — reading `Frank`'s `.fsi`/`.fs` source directly (not just its release notes or docs), designing the exact code changes, and tracking every place the new packages either caught a real bug, saved a design step, or cost extra investigation before the code could be trusted. Nothing below is speculative; every claim cites the specific file/behavior that produced it.

## Verdict

Net positive, with one real caveat. `negotiate { }`, the `descriptor { }`/`describe { }`/`rdf { }` CEs, and the shared `link` mechanism measurably **improved correctness** — each caught or would have prevented a class of bug the hand-rolled code was silently carrying. They also **accelerated the drafting pass**: once a signature was confirmed from the shipped `.fsi` file, the corresponding F# was written once and trusted, with no speculative compile-fix cycles anticipated. The caveat: the new unconditional, app-wide `link` providers (`useAlps`/`useJsonHome`/`useOpenApi`) have a real, **undocumented** interaction gap with per-request conditional logic — the kind of gap an AI agent (or a human skimming release notes) would ship past without noticing, and did require dropping to implementation-level reading (not just the public `.fsi` surface) to catch.

## What accelerated the work

**Shipped `.fsi` files as ground truth.** Every public surface in `Frank`, `Frank.Alps`, `Frank.JsonHome`, and `Frank.Rdf` ships a `.fsi` alongside its `.fs` — exact signatures, XML-doc rationale, and explicit call-out of gotchas (e.g. `NegotiateBuilder.fsi`'s own comment on the `Task<unit>` vs `RequestDelegate` overload trap, frank-fs/frank#492). This is unusually disciplined for an F# library and is exactly the artifact that removes hallucination risk from an AI-assisted workflow: every function signature and CE operation used in the plan (`negotiate`'s `accepts` overloads, `descriptor { }`'s custom operations, `Doc.writeJsonLd`'s `TextWriter` contract, `link`'s two overloads) was taken verbatim from a `.fsi` file, not inferred from a sample or guessed from a name. Zero of the drafted code in the plan required a signature correction once written.

**`RELEASE_NOTES.md`'s density.** The 7.3.2 entry documents not just what changed but *why*, including named issue numbers, the exact behavioral edge cases (`q=0` exclusion, wildcard-must-be-registered-last, `Accept-Encoding`-style routing-layer dispatch), and a previously-shipped-and-fixed bug (#492) with its root cause spelled out. That last one directly prevented a real bug from landing in this migration: `negotiate { }`'s two representations in Task 2 are wrapped in explicit `RequestDelegate(...)` specifically because the release notes named the failure mode a bare lambda would hit.

**`negotiate { }` replacing hand-parsed `Accept` matching is a genuine correctness upgrade, not just a style change.** The code it replaces (`Accept.ToString().Contains "application/ld+json"`) is wrong in ways the original test suite never exercised: it does not respect `q=0` exclusion, and `.Contains` can false-positive on the substring appearing anywhere in the header (e.g. inside an unrelated parameter). `negotiate { }` implements real RFC 9110 §12.5.1 selection at the routing layer. This upgrade was "free" — swapping the mechanism required no design work beyond mapping the existing two branches onto two `accepts` cases.

**Frank.Alps's `binds` validation caught a real, pre-existing bug in the hand-rolled ALPS document**, not a hypothetical one: `reset` was authored as ALPS type `idempotent` while actually implemented as a POST that creates a brand-new game resource on every call (not idempotent by ALPS's own definition — `PUT`/`DELETE` are the only methods that type permits). The hand-rolled JSON string had no way to catch this; it would have shipped indefinitely. `AlpsDocument.validate`'s method/type check turns it into a hard host-startup failure the moment `binds` is wired, which is exactly the moment the mismatch becomes actionable. This is the single clearest "the type system found a bug hand-rolled JSON couldn't" data point in this migration.

**Compile-checked references (`href`, `rt`, `contains` all take `Descriptor` values, not strings) turn a whole class of bug into a compiler error.** The hand-rolled profile's correctness on this axis was enforced entirely by a runtime test (`DiscoveryContentTests`' "every href in the profile resolves to a real descriptor id" — a test that exists *because* the string-based version had no other guarantee). `Frank.Alps.Descriptor`'s `href`/`rt` fields hold `Descriptor` values directly; a dangling reference cannot compile. The runtime test becomes redundant with the type system rather than a substitute for it — though it is kept in the plan anyway, since it still guards against the *authoring* mistake of forgetting to nest a reference at all.

## Where it cost extra investigation

**The unconditional, app-wide `link` provider design has no documented interaction with per-request or per-flag conditional logic, and this is a real gap, not a minor one.** `useAlps`, `useJsonHome`, and `useOpenApi` each register their `rel="profile"`/`rel="home"`/`rel="service-desc"` `Link` contribution as `fun (_: HttpContext) -> Seq.singleton { ... }` — the request is discarded outright (confirmed by reading `src/Frank.Alps/AlpsDocument.fs`, `src/Frank.JsonHome/WebHostBuilderExtensions.fs`, and `src/Frank.OpenApi/WebHostBuilderExtensions.fs` directly; none of this is stated in `RELEASE_NOTES.md` or any `.fsi` doc comment). For a general-purpose API this is a defensible default. For `TicTacToe.Web` specifically — an app whose entire purpose is a controlled experimental surface toggled by an env-var flag (`Surface.Sd`) — it is a silent, wire-observable violation of that surface's own stated contract ("Sd: semantic discovery... hides Link/Allow/OPTIONS") the moment any of these three `useX` operations is adopted. Nothing in the public API surface warns about this; the only way to find it was to read the `.fs` implementation, not the `.fsi`. The fix required is a genuinely non-obvious `IStartupFilter`-based workaround, whose correctness depends on understanding `HttpResponse.OnStarting`'s LIFO callback ordering and where in Frank's fixed `WebHostBuilder.Run` pipeline `WebLink.useAppWideLinks` is spliced (`src/Frank/WebHostBuilder.fs:52`, always first, before any `plugBeforeRouting` entry a consumer can add) — a level of framework-internals reasoning well past what the public `.fsi` surface equips a caller to derive on their own.

**The OpenAPI document's route change (`/openapi/v1.json` → `/.well-known/openapi.json`) is not mentioned anywhere in `RELEASE_NOTES.md`'s prose.** It is real (confirmed in `src/Frank.OpenApi/WebHostBuilderExtensions.fs:16`) and it silently breaks this app's existing `TICTACTOE_OPENAPI_ENABLED` gate the moment the core packages are bumped — before any of the new packages in this plan are even touched. This was caught only because the user independently spotted it and asked; an upgrade done by reading release notes alone would have missed it, and the resulting gap (a discovery-surface toggle that silently stops doing anything) is exactly the kind of regression that's invisible until someone specifically probes for it.

**`href`-only nested references (the hand-rolled profile's `{"href": "#player"}` stubs with no `id`) have no direct equivalent in `Frank.Alps.Descriptor`, whose `Id` field is mandatory.** This is a reasonable design choice on the library's part (an id-less descriptor is arguably not a well-formed one), but confirming the workaround — giving the stub a synthetic id and relying on `InheritsFrom` still serializing to a top-level `"href"` key — required reading `Serialization.fs`'s actual `Utf8JsonWriter` calls line-by-line, not just the `.fsi`'s type shapes. The `.fsi` alone under-specifies exactly how a value maps to wire JSON; for anything beyond the common case, the implementation had to be read too.

**`binds`'s ability to attach more than one `Descriptor` to the same endpoint is real and useful, but is not documented anywhere as a feature.** No `.fsi` doc comment and no sample demonstrates calling `binds` twice in one `handler { }` block. It works because `HandlerDefinition.addMetadata` appends (confirmed in `src/Frank/HandlerBuilder.fs`) and `EndpointSurface.allDescriptors` reads `Metadata.GetOrderedMetadata<Descriptor>()` — plural. This let `take-seat` and `make-move` (the same wire action, historically undocumented as such beyond prose) both bind cleanly to their one shared `POST /games/{id}` handler, which is a better outcome than the plan's first draft (which had `take-seat` permanently unbound and dropped from the live document). Finding it required reasoning about list-append semantics from the implementation, not reading a capability list.

## Feature-addition velocity: the direct comparison

The clearest same-shape comparison in this migration is the ALPS profile and the RDF document, since both replace a hand-written string builder with a typed CE:

- **ALPS** (`descriptor { }`): the 11-descriptor tree, including nine leaf position states, two computed "same wire action" transitions, and cross-references between five composite states, was authored in one pass directly from `DescriptorBuilder.fsi`'s custom-operation list, with a design decision (how to represent the hand-rolled JSON's id-less `href` stubs) resolved by reading one additional implementation file. No trial-and-error compilation was needed to discover the right shape.
- **RDF** (`describe { }`/`rdf { }`): the `schema.org/Game` description, including a multi-valued `sameAs` property (two triples sharing a predicate) and a separate `numberOfPlayers` node, mapped onto `describe`/`propertyString`/`propertyNode`/`Doc.merge` directly from `Rdf.fsi`, matching the pattern already demonstrated in `Frank.Rdf.Sample`.

In both cases, the CE's custom-operation names read as a checklist of what the original hand-rolled JSON needed to express, and the `.fsi` file supplied exact types for each. That combination — a CE whose vocabulary maps onto the domain, backed by a signature file with zero ambiguity — is what made this a fast, low-risk port rather than a speculative rewrite. The cost center in every case was not "how do I call this API" (fast, `.fsi`-driven) but "does this library's design assumption match this app's specific, non-default requirement" (slow, implementation-driven) — and that second category is exactly where an app like `TicTacToe.Web`, built around a controlled experimental surface toggle, is more likely than most consumers to hit friction.

## Recommendation

Adopt all three new packages and the `negotiate { }`/`link` mechanisms as planned — the correctness wins are concrete and the drafting velocity was genuinely high. Do not adopt `useAlps`/`useJsonHome`/`useOpenApi`'s automatic `Link` advertisement as a black box; budget for the `IStartupFilter` scrub workaround as a real, non-optional part of the migration cost, not a nice-to-have. If reporting this upstream to the Frank maintainers, the two most actionable findings are: (1) the unconditional app-wide `link` provider closure discards `HttpContext` with no documented escape hatch for per-request gating, and (2) the OpenAPI document path move belongs in `RELEASE_NOTES.md`'s prose, not only in source.
